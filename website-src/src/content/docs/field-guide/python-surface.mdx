Use `sl.context(...)` to configure your execution resources and backend, then
declare inputs and describe SQL or DataFrame work. DataFrames are lazy: building
operations does not execute the query. Start with the complete,
copyable [paid-orders example](/field-guide/start-local-proof).

## Run a local query

The first workflow uses `ctx.read_csv(path)`, `filter(sl.col("status") == "paid")`,
`sort("order_id")`, and `collect(check=True)`. Building that fluent chain does
not execute the query. Collection executes once under the declared allocation.
Execution errors raise typed exceptions by default. Use `check=False` only when
you intend to inspect an unsuccessful report, and check `is_error` before using
its values.

`ctx.read(path)` infers the reader from the extension. Named helpers such as
`read_csv`, `read_json`, `read_parquet`, and `read_vortex` make the boundary explicit.
Pass `schema=` when the input needs a declared type contract. See
[formats and types](/field-guide/runtime-and-io#local-formats).

For generated data, the context provides `from_rows`, `from_batches`, `range`,
and `repeat`. Typed batches require a schema; arbitrary Python callbacks are
not a query execution backend. Resource validation happens before data access.

## Consume results

| Intent | Published 1.0.0 operation | Result |
| --- | --- | --- |
| Collect a small complete result | `plan.collect()` | `Result` with data and execution details; engine-owned columnar data when using native transport. |
| Read schema | `result.schema` | Ordered names and logical types, including empty results. |
| Convert to Python values | `result.to_rows()` | Complete tuple of row mappings; allocates Python objects explicitly. |
| Export columnar data | `result.to_arrow()` | Arrow table; requires optional PyArrow and may convert encoded buffers. |
| Export to pandas or NumPy | `result.to_pandas()`, `result.to_numpy()` | Explicit optional integration with its documented type conversion. |
| Deliver larger supported results | `plan.iter_batches()` or a writer | Bounded delivery rather than an arbitrary-sized Python tuple. |
| Inspect execution | `result.details` | Typed execution envelope with diagnostics, source identity and execution details. |

Small computed-result collection is limited to **65,536 rows and 8 MiB** in this
release. `result_rows` is the wire-oriented row representation; `to_rows()`
restores logical binary, decimal and temporal values. Neither conversion reruns
the source. A query memory allocation does not bound consumer-retained Python objects.

`run()` is the compatibility report-oriented operation; it is not a shortcut
to faster execution. `profile()` performs bounded profiling and returns its
own statistics. Prefer `collect()` for data and an explicit writer for persistence.
The [migration guide](/field-guide/development) explains the compatibility aliases
and changes from earlier releases.

## Consume results in batches

Use a context manager so stopping early closes the iterator:

```python
with plan.iter_batches(batch_rows=1024) as batches:
    for batch in batches:
        consume(batch)  # your application; convert only when needed
    assert batches.report is not None
```

Here `plan` is a supported Vortex or typed-input plan and `consume` is your own
batch consumer. Load other file inputs into Vortex before
batch consumption. Python batch pipes require Linux or macOS; the Windows
CLI-backed package supports collection and writers instead. A batch is provisional until the input is fully drained and
the final report succeeds: a later producer error invalidates completion.
Closing early cancels delivery and does not certify unobserved input.

Use `ctx.from_batches(producer, schema=..., streaming=True)` for supported finite
streaming producers. The subprocess protocol uses at most 2,048 row mappings and
8 MiB per frame. In-process columnar intake and output preserve supported array owners;
process transport serializes buffers. Operator state and consumer retention have
separate memory obligations. See [resources and cancellation](/field-guide/resources).

## Reuse and export

Source preparation can reuse a loaded data file while its source, schema, and
file identities still match. Each execution computes a fresh answer.
`ctx.prepare(...)` prepares source data, while `ctx.session(...)` exposes advanced
session and reuse controls. Ordinary reads use the same preparation machinery
when execution requires it. See the [data lifecycle](/field-guide/execution-routes)
for the distinction between loading data and preparing a query.

The [first workflow](/field-guide/start-local-proof#write-and-reopen) shows
`write_vortex` followed by `read_vortex`. Other named writers are
`write_parquet`, `write_arrow_ipc`, `write_avro`, `write_orc`, `write_csv`,
`write_json`, and `write_jsonl`. Read their
[fidelity and publication limits](/field-guide/runtime-and-io#write-results).

## Reuse columnar results

On Linux/macOS native installations, contexts select native transport by default
unless an explicit CLI configuration selects process execution. A collected
result retains engine-owned columnar data. Pass it to `ctx.from_result(result)`
for subsequent supported work without an Arrow export.
Reuse under the same owner shares the data; transfer to another owner may copy
encoded buffers under the receiving memory allocation. Do not convert to rows merely to chain work.

`ctx.from_vortex_ipc(array_message, dtype_message=...)` accepts complete immutable
messages for the pinned provider within a combined 64 MiB intake limit. Its
[encoded transfer contract](https://github.com/depsilon/shardloom/blob/main/docs/architecture/native-encoded-interchange-2026-10-12.md)
lists the accepted schemas and encodings. For Vortex files, use `read_vortex`.

Use `with sl.context(...) as ctx:` or call `ctx.close()` when finished. Completed
native results keep their independent owner after the context closes.
Closing or cancelling active work has distinct semantics; see
[lifetime and cancellation](/field-guide/resources#lifetime-and-cancellation).
