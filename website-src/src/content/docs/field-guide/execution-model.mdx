SQL and DataFrame operations describe the work. Readers and writers handle
formats. ShardLoom plans and executes the computation, within its
[documented operation and type limits](/field-guide/limitations).

<span id="one-native-pipeline"></span>

## One engine

**Input formats → ShardLoom engine → Output formats**

Choose a source, query, and destination. The engine handles planning, execution,
resource management, and result delivery across supported interfaces. Loading
and reuse are stages in the [data lifecycle](/field-guide/execution-routes).

ShardLoom uses Vortex's columnar representations, encodings, and file-format
capabilities within its execution and storage architecture. Vortex is an
upstream component with its own format and reader contracts. It does not create
a second product or execution mode for users to select.

## Avoid work first

The engine tries to answer from metadata, skip irrelevant segments, and compute
against encoded values before decoding or constructing rows. A dictionary or
repeated value can let an operator process fewer values while preserving an
exact answer.

**Zero-decode** means an operation preserves encoded values. **Zero-copy** means
a boundary avoids copying buffers. These are different properties, neither of
which applies to every operation. Execution reports identify where reading,
decoding, copying, and result conversion occurred when those observations are
available.

## Broader workloads, the same engine

Formats, data types, operators, and connectors extend around the same engine.
Completing support means composing whole read → transform → write workflows
and handling larger data with bounded streaming, shared resource accounting,
and engine-managed spill. Remaining work is tracked in the
[breadth and scale plan](https://github.com/depsilon/shardloom/blob/main/docs/architecture/universal-workflow-completion-2026-10-01.md).

ClickBench is one regression and comparison workload. Its queries and schema do
not define the product's scope. Shared optimizations must also work with other
schemas and supported compositions.

<span id="no-fallback"></span>

## Executed by ShardLoom

Unsupported plans return explicit diagnostics. ShardLoom does not delegate
execution to Spark, DataFusion, DuckDB, Polars, or another query engine.

Approved upstream Vortex array, compute, scan, source, and sink APIs can provide
operations within ShardLoom's feature, policy, and validation boundaries.
Vortex integrations with external query engines are not execution providers.

## Inputs and outputs

Supported CSV, Parquet, and other inputs enter through readers. Format conversion
has real costs; using the same engine does not make all formats equally expensive
to read or write.

Vortex is the highest-fidelity persistence target. Other output formats have
explicit type and metadata limits. A Vortex file written by ShardLoom is a
Vortex file; additional dataset metadata and any required reader extensions
must be documented separately.

See [reading and writing data](/field-guide/runtime-and-io) for supported
formats and limits.

<span id="execution-evidence"></span>

## Execution reports

Reports describe source identity, computation, result conversion, and output.
They distinguish planned operations from performed work and retain exact
diagnostic classifications. Available checks, such as output digests and
reopened-result comparisons, support validation.

The structured report preserves machine identifiers including
`fallback_attempted=false` and `external_engine_invoked=false`. Detailed
[report identifiers](/field-guide/reference#execution-report-identifiers)
belong in the reference. A local execution report, capability listing, and
reproducible benchmark each establish different facts.

Follow the [query walkthroughs](/field-guide/compute-flow) to see how work varies
with a query, and read [performance and benchmarks](/field-guide/benchmark-methodology)
before comparing measurements.
