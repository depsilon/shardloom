## Choose memory and parallelism

Supply memory and parallelism together on the context or terminal operation.
The first workflow selects `memory_bytes=256 << 20, max_parallelism=2` for three
rows. Choose values appropriate to your workload and deployment; importing the
package never selects an allocation.

`ExecutionResources(memory_bytes, max_parallelism)` expresses the same policy.
Use `memory_gb` for whole GiB or `memory_bytes` for exact bytes, not both.
Missing, malformed, or unauthorized allocations fail before dataset access.
Terminal overrides must respect configured resource ceilings.
Environment loading is explicit through `ExecutionResources.from_env()`.

A memory allocation covers the engine reservations accounted for by the selected operation. It is **not a total-process RSS
limit**: optional integrations, Python objects retained by your application,
and unreviewed reader/codec scratch have separate allocation behavior.
The [resource contract](https://github.com/depsilon/shardloom/blob/v1.0.0/docs/architecture/required-execution-resources-2026-10-10.md)
defines inheritance and administrator ceilings.

## Authorize spill

Spill requires an explicit supported policy, a local workspace and a disk quota.
Ordering, aggregation, joins, analytic windows and file/resident-memory pivot
have their own supported strategies. The engine also includes explicitly
admitted relational membership and sampling population pressure paths.
Replay permission does not authorize arbitrary state spill.

Use the [native spill reference](https://github.com/depsilon/shardloom/blob/v1.0.0/docs/reference/native-query-spill.md)
for exact policy examples, types and minimum quotas. Quotas must cover overlapping
inputs, runs and outputs. Unsupported spill configurations fail explicitly.

Normal completion and cooperative cancellation clean owned temporary files.
A process crash can leave owned state. Recovery checks file identities and
refuses unknown or replaced files; do not delete an arbitrary workspace to retry.

## Lifetime and cancellation

Use `with sl.context(...) as ctx:` or call `ctx.close()` to revoke future work.
A context and its sessions share the same lifetime; closing either facade also
closes work built from the other. Completed results keep their independent
owners after close. Release results and exported views when no longer needed.

`ctx.cancel()` stops current work while leaving the context available for later
operations. Native cancellation is cooperative at supported checkpoints; a
blocking provider call must return before cleanup can finish. Process cancellation
terminates the active process and reports that staged cleanup or output publication
may be uncertain. Inspect affected output before retrying.

Closing a batch iterator stops delivery early. Only full drain and a successful
final report certify completion. See the [migration guide](/field-guide/development)
for lifecycle and typed error details.

## Preparation reuse

Retained sources and prepared queries reduce repeated setup. Source, schema,
and file identity checks still run where required; changed inputs invalidate
reuse. Every query executes again, and one-shot producers are not silently
replayed after failure. Keep the selected backend fixed for the context's lifetime.
