The native wheels contain both the extension and CLI. Windows uses its CLI-backed

Exact supported operations still depend on schema and options. Capability or

## Known issues

| Situation | What to do |
| --- | --- |
| No wheel matches the OS, architecture or Python ABI | Use a listed environment or follow the source-build reference. Do not rename a wheel to bypass its platform tag. |
| Computed result exceeds collection limits | Consume admitted batches or write output; requesting a Python tuple does not enable unbounded collection. |
| A process input/result crosses a Python boundary | Expect explicit serialization and bounded protocol frames; it is not zero-copy. |
| Python batch iteration on Windows | Process batch pipes currently require POSIX. Use bounded collection or a writer; Windows batch delivery remains development work. |
| Memory remains live after close | Retained results and consumer objects keep their own owners. Release those references when no longer needed. |
| A query needs spill | Supply an explicit supported spill policy. A replay/output spill policy does not enable spill for every operator. |

## External systems

Local files, local Vortex manifests and partitions, and admitted table-file reads
are the executable data boundaries covered here. Remote writes, catalog transactions,
production object-store services, REST/Flight services and Foundry integration
remain [design and roadmap work](/field-guide/development#roadmap-and-contributor-material).
Arbitrary UDFs, Python callbacks and network/API/model effects need their own
explicit admission; they do not run during capability inspection.

## Release and readiness

The package is available as a technical preview. Operational hardening remains
in progress: a query allocation is not a whole-process RSS ceiling, and reader/codec
scratch and failure coverage have remaining work. The
[local-engine acceptance criteria](https://github.com/depsilon/shardloom/blob/main/docs/release/production-certification-gate.md#local-engine-preview-exit-criteria)
define the support commitment separately from feature availability.

Correctness coverage and [performance evidence](/field-guide/benchmark-methodology)
are separate facts. Available execution does not by itself establish a comparative
performance claim.

## Extending breadth and volume

Development adds supported shapes to the same native engine. The
[development and migration page](/field-guide/development) describes the 0.7.0
API changes and how to distinguish later source work. Immutable published packages
retain their release-time behavior.

## Failure behavior

Unsupported work produces a deterministic diagnostic. ShardLoom never executes
it through Spark, DataFusion, DuckDB, Polars, or another fallback engine.
Use [troubleshooting](/field-guide/troubleshooting) to inspect the structured error.
